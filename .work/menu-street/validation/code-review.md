# 主菜单动态街道代码审查

审查范围：`src/game/menuStreet.ts`、`src/game/menuStreetModel.ts`、`src/game/scenes/MainMenu.ts`、`src/game/menu.ts`；必要时只读核对本地 `node_modules/phaser` 4.2.1 的实际实现。未修改源码、初始化项目、操作浏览器、运行构建/游戏验证或启动服务。以下为源码及投影公式可直接证明的问题，不是运行时截图结论。

## 1. 高优先级：宽窗口中房屋尚未离屏便回收，破坏循环连续性

**位置：** `src/game/menuStreetModel.ts:39–45`、`src/game/menuStreet.ts:153–158, 203–220`。

`houseDepth()` 将房屋前端深度约束在 `[1, 188.2)`，前端到达 `near = 1` 后立即跳回远端。但房屋沿深度延伸 `7.45`，其末端此时仍在 `z = 8.45`；离屏判定也明确使用这个末端。固定的前端回收阈值不能保证宽屏时整栋房屋已离开视域。

具体证据：按 16:9 宽高比的 `1280 × 720` 视图归一化计算，左侧房屋回收前的末端内墙边投影仍为 `x ≈ 292.36`；高度 `6.8` 的房屋该边从 `y ≈ 124.87` 延伸到 `580.90`，明显位于屏幕内，且 `distanceFog(1) = 1`、`visible = true`。下一次前端越过下界，整栋房屋就跳到接近 `188.2` 并因远雾变得不可见。右侧同理。该比例下结果与逻辑尺寸同比缩放无关；当前 `src/game/main.ts:22–24` 使用 `Scale.EXPAND`，没有限制为竖屏。每侧相邻房屋的回收间隔为 `7.8 / 0.8 = 9.75` 秒，所以这不是一次性启动现象，而是持续重复的可见消失。第一栋左侧房屋还从 `z = 1` 起步，宽屏时首个正 delta 就发生回收。

**最小修复：** 使房屋继续前进，直到整栋房屋末端/可见几何退出视域或近裁剪面后才回收；相应调整有界循环区间与远端渐入边界，使新回收对象仍从零雾透明度进入。保留固定对象池、天空和 UI，不需要改变摄像机。不能只靠当前前端 `near` 或仅在近端淡出来掩盖可见回收。

## 2. 中优先级：Canvas fallback 的树木深度固定，远树覆盖近树

**位置：** `src/game/menuStreet.ts:54–58, 183–185, 203–204, 221–224`。

虽然 `ordered` 按远到近遍历，Canvas 分支却将所有 `drawTree()` 的深度参数固定为 `0.9`，最终所有树木 Graphics 的深度均为 `0.9002`。树并未画入按顺序合成的 Canvas，而是独立 Phaser 对象；循环中的绘制调用顺序不会重排 DisplayList。本地 Phaser `src/gameobjects/DisplayList.js:185–208` 使用稳定排序且只比较 `_depth`，因此树仍保持固定创建顺序（同侧 slot 从小到大），初始阶段是近树先渲染、远树后渲染。

具体证据：`travel = 0` 时左侧 slot 5、6 的房屋深度分别为 `40`、`47.8`，二者 alpha 都为 `1`。在 `720 × 1280` 视图中，两棵树冠中心分别约为 `(262.76, 777.30)`、`(276.77, 774.12)`，半轴分别约为 `(9.06, 11.27)`、`(7.76, 9.65)`；按源码椭圆公式可确认二者重叠。因此后创建的远树会在重叠处盖住近树，与 WebGL 分支使用世界深度的遮挡顺序不一致。

**最小修复：** 将第 224 行的 `ctx ? 0.9 : depth` 改为 `depth`，让 Canvas 的独立树木 Graphics 同样按当前世界深度排序。该改动不增加对象、纹理或事件，也不改变 UI 层级。

## 其余重点结论

在本次源码审查范围内，未发现其他有证据的重大缺陷：旅行累计量有界，路面条纹的循环近端已在画面下方；天空/远景不随 update 移动；街道只通过 MainMenu.update 推进，菜单场景暂停后不会继续推进；正常场景切换会触发 shutdown，固定池对象及 Canvas 专用纹理均有清理路径，重返菜单重新创建背景。未发现正常进入/退出流程的对象或纹理持续增长。

本地 Phaser 4.2.1 的 `mesh2d()` 顶点布局、四值三角索引和 `buildOrderedIndices(1, true)` 与调用一致，直接更新 vertices 可被实际提交器读取；CanvasTexture.setSize/refresh/remove 也有对应实现。未发现这些 API 的兼容性错误。未能用版本基线比较旧 UI/角色源码，因此不将其原有逻辑问题或未验证差异列为此次新增缺陷。
